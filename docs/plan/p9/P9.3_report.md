## Decisions and deviations
1. `TicketLifecycleUseCase` takes an extra `messages: Messages` argument (before `encoder`): the in-app `ticket_forwarded` notification for the new office (as today) needs it.
2. Staff comment with `status` is a status change (rows 5-8; the comment is the activity body and sits inside the one status email). With a status equal to the current one it is a plain comment. `change_status` to the same status without a note is a no-op (`activity=None`, no email, no mirror); with a note it is a plain comment.
3. A staff public comment (no status) is only allowed on `new`/`in_progress` (rows 2-3); on solved/closed it raises `InvalidInput` ("reopen it first"). An internal note works on any non-merged ticket and cannot carry a status.
4. Requester sending an internal note or a status in a comment -> `Unauthorized` (403). Staff/admin acting on a request they own go the requester path; staff-only actions (status, forward, priority) raise `Unauthorized` for them.
5. Requester "Solved" on a solved ticket that is no longer awaiting, and "Close" on a closed ticket, are no-ops (`activity=None`); "Solved" on a solved ticket that is still awaiting applies row 13 (clears `awaiting_student`). "Keep open" is refused (422) unless the ticket is solved, or in_progress and awaiting.
6. `change_priority` to the current priority is a no-op (no restart, no hint); priority change needs `new`/`in_progress`.
7. `apply_hint` (row 17) returns a no-op change when neither the office nor the priority changes; a priority-only change writes a `priority` activity, an office change a `forward` activity (actor_role `system`, body `past correction`). It does not add the `forwarded` tag.
8. "admin also gets requester_reply when the ticket has tag `forwarded`": the second planned email uses the `office` template addressed to the admin inbox (the YAML has no `admin` audience for `requester_reply`), so a requester reply on a forwarded ticket sends two emails, a documented exception to "one email per action".
9. `on_created` writes the `created` thread row with the request text as body (public), does not re-save the ticket (the clock already started at creation), skips merged tickets, and runs `deliver` itself (received/requester + received/office). Actor role = the contact's role, else `student`. For a provisional ticket it also sends (PLAN says every action ticket id); a later clarify answer does not send again (idempotent).
10. In-app notifications in `deliver`: the requester gets a `ticket_status` note on staff status changes and staff replies (message = comment); the new office gets `ticket_forwarded` on forwards (as before). No in-app note for requester actions.
11. Hint failures (store, encoder, missing prediction) are logged and never fail the action; `model_category/priority` come from `repo.latest_prediction` (NotFound -> null); the embedding uses `text_norm`, else the raw text.
12. Audit `events` use actor `ticket_lifecycle` and actions `ticket.comment|note|status|forwarded|priority|student_action|created|hint_applied` with `by` and `role` in the payload (the old forward event payload gained `role`).
13. Not touched: the web allow-list `apps/web/src/lib/ai/allowlist.ts` has no rules for `comments`, `priority`, `student-action` yet (P9.6/P9.7 web packages must add them).
