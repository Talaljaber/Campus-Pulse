## Decisions and deviations
1. The clock restart and count reset are done by P9.3's lifecycle (verified by the forward test); not reimplemented.
2. The in-app note reuses `messages.staff.escalated` (config/templates/messages.yaml, "SLA missed (due ...): this X-priority ticket is overdue.") and appends " Second reminder: the admin was informed." for level 2, to avoid editing the shared messages file.
3. Reminder emails are rendered in English (`lang="en"`; office and admin audiences) and use the request text for the context; a missing request just gives an empty text.
4. `SlaReminderUseCase` also takes `sla_hours` (a fifth argument) to compute the second period; the PLAN signature listed four.
5. A failing email, note or audit never undoes a claim (a claimed level is final, so a lost email is not retried; the UI clock still shows the overdue state).
6. The sweep task is scheduled after `call_next` returns (the response object exists; the body may still be streaming). The response is not delayed by the scan.
7. `sla` is None when no journey store is wired (the route answers 501), instead of a reminder scanner without claims.
8. Tag of the route in the OpenAPI document is `staff` (no dedicated tag).

## README text for the honest limit
SLA reminder emails can be late when the service sleeps: the wake-up ping comes from a GitHub scheduled workflow (every 10 minutes, GitHub may delay scheduled runs further under load) plus the cold start of the service, often 10 to 20 minutes in total. The deadline, time left and overdue marker in the UI are computed from `sla_due_at` in the browser, so they are always right; only the email can be late. Render Starter does not sleep, so there the reminders follow the in-process scan (`SLA_SCAN_MINUTES`, 5 minutes) and the sweep after API responses.
