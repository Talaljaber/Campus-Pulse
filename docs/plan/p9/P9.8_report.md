## DecisionFlow on ASK with an exhausted budget (verified in code and by a test)

With `chat_confirmed`, `TriageUseCase.run` builds `ClarificationBudget(max_questions=0)`. In `DefaultDecisionPolicy.decide_with_path`
rule d (`ASK`) needs `budget.remaining > 0`, so it never fires. The policy continues to rule e: `ESCALATE` when
`llm_allowed and ambiguous` (the LLM tiers are usable and no injection flag), else `HUMAN_REVIEW`. So `DecisionFlow.run` never
reaches its `ASK` branch (the `spent` re-run there is for "no bank question applies"). An ambiguous confirmed request therefore ends in a
tier-1 decision, or in a provisional ticket (`provisional`, tag `unconfirmed`, status `human_review`, review item queued). Covered by
`test_confirm_never_asks_again_and_opens_a_provisional_ticket`. `OUT_OF_SCOPE` is decided before the budget and still returns
`out_of_scope` with no ticket (a proposal is never offered for such text, so confirm cannot normally reach it).

## Behaviour choices to know

- Order in a turn: validate -> classify the last user message -> distress (full triage persisted, existing reply, no LLM) -> no
  LLM / LLM failure -> `mode: fallback` -> LLM call 1 -> intent handling. Distress is handled even when the LLM is off.
- `request_text` = user messages after the last assistant message of kind `proposal`/`ticket`, joined by newline, last 1000 chars.
- A clarifying question in a turn is returned as plain `reply` text (question and options inline), no `proposal`. The one-question
  budget in a turn is "spent" when `request_text` has more than one user message (the client does not send `asked` in a turn).
  The plain form uses `asked` and `answer` and gets the structured `question`.
- Reply post-check: the proposal reply must contain the localized department name and none of the banned phrases, else the template.
  The banned-phrase check also guards `chat`, `announcement` and `decline` replies (template on a hit).
- `confirm` intent without a valid token: nothing is recorded and the reply is a template (the model's text is never shown, so it cannot
  claim a recorded request). A token that was sent but is expired/forged/foreign inside a turn gives the `expired` template and
  `clear_proposal: true` (only `POST /v1/chat/confirm` answers 422).
- The proposal's department/priority come from the classifier on the proposed text; a hint >= 0.85 changes category (so office) and raises
  priority only; `why` carries the model's own category/priority and 3 neighbours. `ProposalOut.hint` has no text of the other request.
- Hint application on confirm: `apply_hint` runs only for a plain `ticket` action (not an incident merge); its `LifecycleChange` is
  delivered in the background before `on_created` (via a `later` list passed to `turn`/`confirm`).
- Preview uses no LLM tiers, so the preview's labels are the model's own; a confirmed request may be refined by tier 1 if the policy escalates.

## Deviations from the brief / PLAN (all internal or additive; no DTO shape of PLAN (f) changed)

1. `ChatAgent.reply(ctx, messages)` / `phrase(ctx, facts)` take a `ChatContext` instead of a ready `system` string: the adapter renders the
   prompt file (keeps the prompt out of application code, and lets the test check "Arabic -> prompt asks for Arabic" on the real adapter).
2. `ChatUseCase.turn` / `confirm` take an extra optional `later` list of callables (hint delivery); routes turn it into background tasks.
3. Shapes PLAN left open: `ProposalOut.question: ClarificationOut | null`, `hint: HintOut{hint_id, category, priority, sim} | null`,
   `why: ProposalWhyOut{category: CategoryOut, priority: PriorityOut, neighbors: NeighborOut[<=3]}`, `action_kind: ActionType`,
   `token` empty while `question` is set, `ChatTurnResponse.mode: "agent" | "fallback"`. **P9.9 should read these from `types.gen.ts`.**
4. In the plain form (`chat_preview`) a distress text is triaged and persisted and answered as `question{question_id: "distress",
   text: <supportive reply>, options: []}` with an empty token (the shape has no message field).
5. `TriageRequest.chat_confirmed` is part of the `/v1/triage` body schema (PLAN names it there); the route forces it to false.
6. `ApiServices.chat` is None without `AI_SERVICE_TOKEN` (proposals cannot be signed); every route answers 401 in that case anyway.
7. `apps/web/src/lib/ai/allowlist.ts` is NOT changed (web is P9.9): it needs rules for `POST chat/turn`, `chat/preview`, `chat/confirm`.
