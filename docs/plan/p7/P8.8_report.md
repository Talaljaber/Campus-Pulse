## Findings the lead should know

1. **`/health` does not touch the database.** `routes/health.py` `health_of` only reports wiring and RSS. The brief assumed it did, so the keep-alive does its own DB touch through Supabase Auth and a REST read with the demo student session (anon cannot read any table by design, RLS). Optional for the backend owner: a cheap `select 1` in `/health` would make the uptime ping prove the database too.
2. **A fresh Supabase project (local or new hosted) gives `service_role` no table grants**, because the migrations rely on default privileges that new CLI/cloud defaults no longer give (`auto_expose_new_tables` in `supabase/config.toml` is unset). The API then gets `permission denied for table faq`. The local setup grants them in the local database; the hosted project is unaffected as it already works. Do not recreate the hosted project during judging. A migration with explicit `grant ... to service_role` would remove the trap (needs a migration owner; not done here, outside this package).
3. **Render plan and Supabase tier cannot be verified from the repo.** `render.yaml` says `plan: starter` (paid, no spin-down). The Supabase tier is unknown; Free projects pause after about a week of inactivity.
4. The dev laptop already runs two other local Supabase projects on 54322 and 56321-56324; the test used an alternate-port copy via `DEMO_SUPABASE_WORKDIR`. `supabase start` also needs `-x logflare,...` on Windows (the analytics container fails), which the script passes.
