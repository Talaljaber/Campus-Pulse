# P10.19: an admin knowledge base the chat can quote

User request, 2026-11-08: give the admin a place to upload files, or paste text, that become part of the
assistant's knowledge.

A real university keeps its rules and procedures in handbooks and office pages: refunds, the add/drop
period, library hours, how to reset a password. The assistant should be able to answer from them, citing
the document. It must never make up what the document does not say.

## Contract (already on `main`, do not change it)

These are in `dto.py`, `api_contract.py`, `openapi.json` and `apps/web/src/lib/ai/types.gen.ts`.

**Endpoints** (admin only, through the web proxy):

| Endpoint | Body | Returns |
|---|---|---|
| `POST /v1/admin/knowledge` | multipart: `title` (1–200 characters), optional `office`, and either `file` (PDF, .txt or .md, at most 5 MB) or `text` (pasted, at most 200,000 characters) | `KnowledgeDocOut` |
| `GET /v1/admin/knowledge` | none | `KnowledgeListOut` (`{documents: [...]}`, newest first) |
| `DELETE /v1/admin/knowledge/{doc_id}` | none | `KnowledgeDeleteOut` (`{id, deleted}`) |

**Shapes:**
- `KnowledgeDocOut`: `id`, `title`, `filename` (null for pasted text), `office` (one of the six office codes,
  or null for campus-wide), `char_count`, `chunk_count`, `uploaded_by` (the uploader's alias), `created_at`.
- `ChatTurnResponse.sources: ChatSourceOut[]`. Each source has `id` (`announcement:<id>` or
  `knowledge:<document id>`), `kind` (`announcement` or `knowledge`) and `title`. These are the sources the
  reply actually used; the web shows them as "From: <title>".

**Current state:** the real routes are stubs in `frameworks/routes/knowledge.py` that answer 501. The mock
app serves fixtures.

## Backend (stream A)

1. **Migration** `supabase/migrations/0020_knowledge.sql`:
   - Tables:
     - `knowledge_documents`: id, title, filename, office (checked against the six codes, or null),
       char_count, chunk_count, uploaded_by (alias text), created_at.
     - `knowledge_chunks`: id, document_id (FK, on delete cascade), ord, text, `embedding
       extensions.vector(384)`, created_at.
   - Indexes:
     - a cosine index on the chunk embeddings, as the other vector tables do (see
       `0005_vectors.sql`);
     - an index on `document_id`.
   - Access:
     - RLS enabled on both tables.
     - `revoke all` from anon and authenticated; `service_role` gets everything. The AI service is the
       only reader and writer.
   - Extend `match_vectors` with a `knowledge` collection that returns id, text and sim, plus meta
     `{document_id, title, office}`. Read the current function in `0005_vectors.sql` first and keep every
     existing collection unchanged.
   - Use `create or replace`, so the migration can be applied to the hosted project.
   - Do not apply it to any database. The lead applies it after review.
2. **Text extraction:**
   - PDF goes through `pypdf`: add it, pinned, to `services/ai/requirements-api.txt` only, never
     `requirements.txt`, so `predict.py` is unchanged.
   - .txt and .md are decoded as UTF-8; on failure, as `utf-8-sig`, then refused.
   - Decide the type from the bytes, as `TicketFilesUseCase` does (a `%PDF-` header means PDF; otherwise
     valid UTF-8 text).
   - Refuse with 422 when the file is empty, unreadable, over 5 MB, or has no text (for example a scanned
     PDF), with a clear message.
   - Normalise whitespace.
3. **Chunking:**
   - About 800 characters per passage with 100 overlap, split on paragraph, then sentence boundaries.
   - At most 300 passages per document; refuse longer documents with 422 and say so.
4. **Embedding:**
   - Use the same raw ONNX encoder the FAQ uses (`offline.raw_encoder`), in batches. No translation and no
     LLM.
   - Write through a new `VectorStore` collection `knowledge` in `PgVectorStore` (`COLLECTIONS` and
     `FILTER_KEYS`) and in the local numpy store, so the use-case tests run offline.
   - The document row is written first, then the chunks. On a failure, delete the document, so no
     half-written document stays.
5. **Use case** `application/use_cases/knowledge.py` (`KnowledgeUseCase`):
   - `upload(caller, title, office, text | file bytes + name)`, `list()`, `delete(doc_id)` (NotFound →
     404), and `search(text, k=3) -> list[KnowledgeHit]`.
   - Admin role is checked in the use case too, not only by the route.
   - Wire it in `ApiServices` (`composition/api.py`) and `composition/online.py`.
   - Replace the stub route bodies.
6. **Chat grounding** (`ChatUseCase._context` and `_announcement_context`):
   - For every turn, search the knowledge base with the last user message: top 3 hits with
     `sim >= KNOWLEDGE_MIN_SIM`.
   - Calibrate the default threshold on a real document so that unrelated questions get nothing. e5
     cosine scores are high, so try values around 0.80–0.85. Make it a setting in `config/settings.py`
     plus `.env.example`.
   - Add the hits as `GroundingSource(kind="knowledge", id="knowledge:<doc id>", text="<title>:
     <passage>")`. Extend the `kind` literal.
   - Include them in the prompt's CURRENT SOURCES block. The prompt (v4) already says facts may come only
     from CURRENT SOURCES and must be cited in `source_ids`.
   - If the prompt needs a sentence about knowledge documents, write a new `chat_agent_v5.md` and bump
     `prompt_version`; never edit v4 in place.
   - Fill `ChatTurnResponse.sources` from the `source_ids` the model cited, keeping only ids that were
     really offered this turn. Use announcement titles too. At most 5.
   - A failing knowledge read must never break a chat turn; log it and continue without it.
7. **Tests** (pytest, with fakes):
   - upload of text, .txt and a small PDF made in the test (pypdf can write one, or use a minimal PDF
     byte string);
   - refusal of an empty file, a binary or unknown type, too large, too many passages, and non-admin;
   - list and delete (cascade);
   - chat: a matching question gets the passage as a source and `sources` filled; an unrelated question
     gets no knowledge source; a source id the model invents is dropped; the knowledge store failing
     still answers.
   - Then run `ruff`, `mypy --strict services/ai/campuspulse_ai`, and the default pytest set. Four tests
     already fail on main; leave them.
8. **Docs:** README Disclosures gets one line, saying documents are embedded locally with e5 and only the
   matching passages are sent to the chat LLM. Write the "Stream A report" section here.

     `tickets/{id}/files`.
   - Update the allow-list tests.
3. **The screen** `components/admin/KnowledgeScreen.tsx`. Calls go through a hook or lib module, because
   components may not import `@/lib/ai/browser` (an eslint rule).
   - **Upload form:**
     - Title is required. Office is a select with "Whole campus" plus the six offices.
     - A "Upload a file" or "Paste text" switch.
     - The file input accepts `.pdf,.txt,.md` and checks 5 MB before sending. The textarea shows a
       character count.
     - An Add button with a loading state. On success, a toast and the new row on top of the list. On a
       422, show the server's message.
   - **Document table** (`DataTable`): title, office, file name or "Pasted text", passages, uploaded by,
     date. Each row has a Delete button with a confirm dialog (`ui/Dialog`).
   - **Empty state:** "No documents yet. Add a handbook or a policy page; the assistant will quote it
     when it answers."
   - A short note: "The assistant answers from these documents and names the one it used. It will not
     guess beyond them."
   - English and Arabic (`i18n/en.ts` and `ar.ts` with the same keys), right to left, and no sideways
     scroll on a phone.
4. **Chat sources:** when a turn response has `sources`, show a small line under the assistant message,
   "From: <title>" / "المصدر: <title>", for each source. Not a link; muted text with a small book icon.
5. **Tests:**
   - vitest for the screen (upload text, upload a file, a 422 message, delete with confirm, empty state),
     the allow-list, and the sources line;
   - an e2e test in `e2e/admin-basic.spec.ts` against the mock API (the fixtures already exist) and the
     fake Supabase;
   - run `tsc`, `eslint` and `vitest`, and the admin and student e2e specs.
