# P10.18: chat corrections, closing requests, status cards, and a plain chat box

User request, 2026-11-08. Real scenario: a student recorded a ticket with the wrong room (H302 instead
of H203).
- They cannot fix it from the chat.
- Writing the request again with the right room keeps the wrong ticket open. The new message either lands
  on the old ticket as a follow-up comment (`_repeat_turn`) or opens a second ticket.

The assistant must notice this case and ask. If the student made a mistake, it closes the wrong ticket and
opens a corrected one. If it is a separate problem, it opens a new ticket and leaves the old one alone.

The student can also close a request from the chat and ask about the status of their requests. Status
answers show a card with a soft animation per status. The microphone and the demo strip are removed, and the
message box looks like any AI chatbot's.

## Contract (already on `main`, do not change it)

These are in `services/ai/campuspulse_ai/application/dto.py`, `services/ai/openapi.json` and
`apps/web/src/lib/ai/types.gen.ts`.

- `ChatTicketOut`: `ticket_id`, `number`, `title`, `office`, `category`, `priority`, `status`,
  `awaiting_student`, `created_at`, `resolved_at`. `number` comes from `domain.journey.ticket_number`.
  `status` is one of `new | in_progress | solved | closed | merged`. This is always one of the caller's own
  tickets.
- `ChatCorrectionOut`: `ticket` (`ChatTicketOut`) and `old_text` (the first 300 characters of the old
  request text).
- `ChatTurnResponse` gains three fields:
  - `tickets: ChatTicketOut[]`: status cards. Default empty, at most 10.
  - `correction: ChatCorrectionOut | null`: set together with `proposal`. The proposal is the corrected
    request, and `correction.ticket` is the open ticket it would replace.
  - `withdraw: ChatTicketOut | null`: asks the student to confirm closing that open ticket.
- `ChatConfirmRequest` gains `replace: bool = false`.
- `ChatConfirmResponse` gains `closed_ticket: ChatTicketOut | null`.

## Backend (stream A)

Files: `application/use_cases/chat.py`, `chat_ports.py`, `proposals.py`, `adapters/llm/chat_agent.py`,
`config/chat_agent.yaml`, and a new prompt `config/prompts/chat_agent_v4.md` (v3 stays as it is; bump
`prompt_version` to `chat-v4`). Plus tests.

1. **The student's tickets in the agent context.** List the caller's recent tickets (open ones plus solved
   or closed in the last 30 days, at most 8, newest first). Give the agent a DATA block "THE PERSON'S
   REQUESTS", one line each: number, status, office, created date, and the first ~200 characters of the
   request text. Read through the `Repository`. Add a port method if needed, and implement it in both
   store adapters (`adapters/store/inmemory.py` and `supabase_store.py`, filtering on `requester_alias` or
   the request's alias as `open_tickets_for_alias` does). A failing read gives an empty list, never an
   error.
2. **New agent intents (prompt v4).** The output JSON gains `ticket_refs` (a list of ticket numbers) and
   `corrected_text` (a string).
   - `status`: the person asks how their request or requests are going. The reply states the status in
     plain words, using only the DATA block. The server returns `tickets` for the refs, or every listed
     ticket when there are none. Refs that are not the caller's are ignored.
   - `correct`: the person says a recorded request has a wrong detail ("I wrote H302, it is H203"), or
     sends the same problem as an open request with a different place, room, building, course or date.
     `ticket_refs` holds the one old ticket. `corrected_text` holds the full corrected request in the
     person's words with the fix applied (the old ticket's text with the detail replaced, plus anything
     new).
   - `withdraw`: the person wants to cancel or close one of their open requests. `ticket_refs` holds that
     ticket.
   - `separate`: a PENDING PROPOSAL replaces #n and the person says it is a different problem. Confirm it
     with `replace=false`.
   - The existing `confirm` intent: when the pending proposal is a correction, a typed "yes" confirms it
     with `replace=true`.
3. **Server handling** in `ChatUseCase._answer`. The server owns every decision; the model's refs are only
   hints, checked against the caller's own ticket list.
   - `status` → `_plain`-like response with `tickets` filled. Add a template fallback if the reply fails
     `_safe`.
   - `correct` → the ref must be one of the caller's tickets with status `new` or `in_progress`.
     Otherwise treat the turn as a normal `request`. Build the proposal from `corrected_text`. If that is
     empty, use `old_text` plus the last user message. Go through `_propose`: the classifier and decision
     policy still decide office and priority, and a clarifying question is still possible. Sign the token
     with a new optional claim `replaces` (ticket id) in `ProposalClaims`. Keep old tokens without the
     field valid. Return `proposal` and `correction` together. The reply asks: "Did you mean to fix #n?
     I can close it and record the corrected request, or keep both." Use a template per language (en/ar)
     that names the number.
   - `withdraw` → the ref must be an open ticket of the caller. Return `withdraw` with a reply asking
     "Close request #n?". The client calls the existing student-action endpoint itself, so the server
     closes nothing here.
   - `separate` with a valid pending token → confirm with `replace=false`.
   - **Repeat logic.** In `_repeat_turn`, when the preparer's `duplicate_of` ticket matches but the new
     text differs in a place, room or building, do not comment on the old ticket. Return the correction
     proposal instead, exactly as for `correct`. A cheap check: compare the extracted building and room
     entities if available, or rely on the agent's `correct` intent. Prefer the intent and keep the
     heuristic minimal.
4. **Confirming with `replace=true`.** Use `ChatUseCase.confirm` and the `confirm` path inside a turn.
   1. Open the corrected ticket as today. The duplicate guard must not block it against the ticket it
      replaces.
   2. Then close the old ticket through `TicketLifecycleUseCase.student_action(old_id, caller, "close")`.
   3. Add a public comment on the old ticket: "Closed by the requester: replaced by #<new> (corrected
      details)." Use the existing `comment` method, best effort.
   4. Fill `closed_ticket`.
   - **Only close when** the token's `replaces` is set, belongs to the caller, and is still open.
     `replace=true` without a `replaces` claim is ignored.
   - With `replace=false`, open the new ticket and leave the old one alone.
   - The confirmed reply names both numbers ("Recorded #new. #old is closed.") in en and ar.
5. **Route.** `frameworks/routes/chat.py` passes `replace` through. Update the mock fixtures as needed.
   Regenerate `openapi.json` and `docs/api/endpoints.md` only if the contract had to change, and say so in
   the report.
6. **Tests** (pytest, fakes in `tests/fixtures`):
   - each intent;
   - refs to another person's ticket are ignored;
   - `replace=true` closes the old ticket only when it is the caller's and open, and never without the
     claim;
   - a typed "yes" on a correction replaces;
   - `separate` keeps both;
   - old tokens without `replaces` still confirm;
   - the H302 → H203 scenario end to end with the fake agent.
   - Then run `ruff`, `mypy --strict services/ai/campuspulse_ai`, and the default pytest marker set. Four
     tests fail on `main` today; leave them alone: `test_api_chat` double-confirm, `test_architecture`,
     `test_allowlist` whitespace, `test_domain_values` recipient policy.

Rules: pinned model, temperature 0. Never let model text claim a ticket was closed or recorded unless the
server did it.
