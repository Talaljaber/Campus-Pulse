# P10.18: chat corrections, closing requests, status cards, and a plain chat box

User request, 2026-11-08. Real scenario: a student recorded a ticket with the wrong room (H302 instead
of H203).
- They cannot fix it from the chat.
- Writing the request again with the right room keeps the wrong ticket open. The new message either lands
  on the old ticket as a follow-up comment (`_repeat_turn`) or opens a second ticket.

The assistant must notice this case and ask. If the student made a mistake, it closes the wrong ticket and
opens a corrected one. If it is a separate problem, it opens a new ticket and leaves the old one alone.

The student can also close a request from the chat and ask about the status of their requests. Status
answers show a card with a soft animation per status. The microphone and the demo strip are removed, and the
message box looks like any AI chatbot's.

## Contract (already on `main`, do not change it)

These are in `services/ai/campuspulse_ai/application/dto.py`, `services/ai/openapi.json` and
`apps/web/src/lib/ai/types.gen.ts`.

- `ChatTicketOut`: `ticket_id`, `number`, `title`, `office`, `category`, `priority`, `status`,
  `awaiting_student`, `created_at`, `resolved_at`. `number` comes from `domain.journey.ticket_number`.
  `status` is one of `new | in_progress | solved | closed | merged`. This is always one of the caller's own
  tickets.
- `ChatCorrectionOut`: `ticket` (`ChatTicketOut`) and `old_text` (the first 300 characters of the old
  request text).
- `ChatTurnResponse` gains three fields:
  - `tickets: ChatTicketOut[]`: status cards. Default empty, at most 10.
  - `correction: ChatCorrectionOut | null`: set together with `proposal`. The proposal is the corrected
    request, and `correction.ticket` is the open ticket it would replace.
  - `withdraw: ChatTicketOut | null`: asks the student to confirm closing that open ticket.
- `ChatConfirmRequest` gains `replace: bool = false`.
- `ChatConfirmResponse` gains `closed_ticket: ChatTicketOut | null`.

## Backend (stream A)

Files: `application/use_cases/chat.py`, `chat_ports.py`, `proposals.py`, `adapters/llm/chat_agent.py`,
`config/chat_agent.yaml`, and a new prompt `config/prompts/chat_agent_v4.md` (v3 stays as it is; bump
`prompt_version` to `chat-v4`). Plus tests.

1. **The student's tickets in the agent context.** List the caller's recent tickets (open ones plus solved
   or closed in the last 30 days, at most 8, newest first). Give the agent a DATA block "THE PERSON'S
   REQUESTS", one line each: number, status, office, created date, and the first ~200 characters of the
   request text. Read through the `Repository`. Add a port method if needed, and implement it in both
   store adapters (`adapters/store/inmemory.py` and `supabase_store.py`, filtering on `requester_alias` or
   the request's alias as `open_tickets_for_alias` does). A failing read gives an empty list, never an
   error.
2. **New agent intents (prompt v4).** The output JSON gains `ticket_refs` (a list of ticket numbers) and
   `corrected_text` (a string).
   - `status`: the person asks how their request or requests are going. The reply states the status in
     plain words, using only the DATA block. The server returns `tickets` for the refs, or every listed
     ticket when there are none. Refs that are not the caller's are ignored.
   - `correct`: the person says a recorded request has a wrong detail ("I wrote H302, it is H203"), or
     sends the same problem as an open request with a different place, room, building, course or date.
     `ticket_refs` holds the one old ticket. `corrected_text` holds the full corrected request in the
     person's words with the fix applied (the old ticket's text with the detail replaced, plus anything
     new).
   - `withdraw`: the person wants to cancel or close one of their open requests. `ticket_refs` holds that
     ticket.
   - `separate`: a PENDING PROPOSAL replaces #n and the person says it is a different problem. Confirm it
     with `replace=false`.
   - The existing `confirm` intent: when the pending proposal is a correction, a typed "yes" confirms it
     with `replace=true`.
3. **Server handling** in `ChatUseCase._answer`. The server owns every decision; the model's refs are only
   hints, checked against the caller's own ticket list.
   - `status` → `_plain`-like response with `tickets` filled. Add a template fallback if the reply fails
     `_safe`.
   - `correct` → the ref must be one of the caller's tickets with status `new` or `in_progress`.
     Otherwise treat the turn as a normal `request`. Build the proposal from `corrected_text`. If that is
     empty, use `old_text` plus the last user message. Go through `_propose`: the classifier and decision
     policy still decide office and priority, and a clarifying question is still possible. Sign the token
     with a new optional claim `replaces` (ticket id) in `ProposalClaims`. Keep old tokens without the
     field valid. Return `proposal` and `correction` together. The reply asks: "Did you mean to fix #n?
     I can close it and record the corrected request, or keep both." Use a template per language (en/ar)
     that names the number.
   - `withdraw` → the ref must be an open ticket of the caller. Return `withdraw` with a reply asking
     "Close request #n?". The client calls the existing student-action endpoint itself, so the server
     closes nothing here.
   - `separate` with a valid pending token → confirm with `replace=false`.
   - **Repeat logic.** In `_repeat_turn`, when the preparer's `duplicate_of` ticket matches but the new
     text differs in a place, room or building, do not comment on the old ticket. Return the correction
     proposal instead, exactly as for `correct`. A cheap check: compare the extracted building and room
     entities if available, or rely on the agent's `correct` intent. Prefer the intent and keep the
     heuristic minimal.
4. **Confirming with `replace=true`.** Use `ChatUseCase.confirm` and the `confirm` path inside a turn.
   1. Open the corrected ticket as today. The duplicate guard must not block it against the ticket it
      replaces.
   2. Then close the old ticket through `TicketLifecycleUseCase.student_action(old_id, caller, "close")`.
   3. Add a public comment on the old ticket: "Closed by the requester: replaced by #<new> (corrected
      details)." Use the existing `comment` method, best effort.
   4. Fill `closed_ticket`.
   - **Only close when** the token's `replaces` is set, belongs to the caller, and is still open.
     `replace=true` without a `replaces` claim is ignored.
   - With `replace=false`, open the new ticket and leave the old one alone.
   - The confirmed reply names both numbers ("Recorded #new. #old is closed.") in en and ar.
5. **Route.** `frameworks/routes/chat.py` passes `replace` through. Update the mock fixtures as needed.
   Regenerate `openapi.json` and `docs/api/endpoints.md` only if the contract had to change, and say so in
   the report.
6. **Tests** (pytest, fakes in `tests/fixtures`):
   - each intent;
   - refs to another person's ticket are ignored;
   - `replace=true` closes the old ticket only when it is the caller's and open, and never without the
     claim;
   - a typed "yes" on a correction replaces;
   - `separate` keeps both;
   - old tokens without `replaces` still confirm;
   - the H302 → H203 scenario end to end with the fake agent.
   - Then run `ruff`, `mypy --strict services/ai/campuspulse_ai`, and the default pytest marker set. Four
     tests fail on `main` today; leave them alone: `test_api_chat` double-confirm, `test_architecture`,
     `test_allowlist` whitespace, `test_domain_values` recipient policy.

Rules: pinned model, temperature 0. Never let model text claim a ticket was closed or recorded unless the
server did it.

## Stream A report

Branch `p10/18-backend` (from `0ae4b8e`). The contract is unchanged: `dto.py` and `openapi.json` are as on
`main`. Only `docs/api/endpoints.md` was regenerated, for four new mock fixtures.

### What was built

- **Token claim.** `ProposalClaims.replaces: str | None = None` (`proposals.py`). The field is written only
  when it is set, so a token without it has exactly the old bytes. Tokens signed before P10.18 verify and
  confirm (tested with a hand-built old-format token).
- **Recent tickets.** There is a new port method, `Repository.recent_tickets_for_alias(alias, since, limit=8)`.
  It returns open tickets plus solved or closed ones resolved at or after `since`, newest created first.
  Merged tickets are excluded. It is implemented in `InMemoryRepository` and in `SupabaseRepository` (two
  small queries, merged), and there is a contract test.
  - `ChatUseCase._my_tickets` reads 30 days and at most 8 tickets. It keeps only tickets whose request alias
    is the caller's. A failing read gives `[]`.
  - The open-ticket read reuses the request texts it already has.
- **Agent context.** `ChatContext.requests` holds one line per ticket, in the form `#<NUMBER> | status: <s> |
  office: <English dept> | created: <YYYY-MM-DD> | text: <first 200 chars>`.
  - It is rendered as a JSON array in the DATA block `THE PERSON'S REQUESTS` of `config/prompts/chat_agent_v4.md`.
  - The pending-proposal summary adds `(a correction: it replaces request #N)` when the token has `replaces`.
- **Prompt v4.**
  - It adds the intents `status`, `correct`, `withdraw` and `separate`, and the output fields `ticket_refs`
    and `corrected_text`.
  - Its fictional few-shot examples include H302→H203 in English, Arabic and Arabizi.
  - `chat_agent.yaml` points to v4 with `prompt_version: chat-v4`. The model id and temperature 0 are
    unchanged, and v3 is untouched.
- **Adapter** (`adapters/llm/chat_agent.py`).
  - `ticket_refs` is normalized: `#ab12cd34` → `AB12CD34`, only 8 hex characters, at most 5, no duplicates.
    `corrected_text` is trimmed to 1000 characters.
  - Malformed hints are dropped rather than failing the turn.
  - The grounding check no longer rewrites `correct`, `withdraw` or `separate` into `chat`, because their
    text is never shown. The server answers those with templates.
- **Server** (`ChatUseCase._answer`). The model's refs are only hints, and every one is checked against the
  caller's own ticket list.
  - `status`:
    - `tickets` holds the cards for the valid refs, or for all listed tickets when there are none (newest
      first, at most 10).
    - The model's words are kept only when they pass `_clean` and name no 8-hex number outside the list.
      Otherwise the reply is the `status` template.
    - With no tickets, the reply is `status_none`.
  - `correct`:
    - The ref must be the caller's ticket and `new` or `in_progress`. Otherwise the turn is an ordinary
      `request`.
    - The corrected text comes from `corrected_text`, or else from the old text with its single room code
      swapped for the new one. If that fails, it is the old text plus the last user message.
    - The text goes through `_propose` with `replaces=<old id>`, so a clarifying question is still possible.
    - The response returns `proposal` and `correction`, with the `correction` template as the reply.
    - A "correction" with the very same words as the open ticket is treated as a repeat and gets the
      `already_open` reply.
  - `withdraw`:
    - With a valid open ref, the response sets `withdraw` and uses the `withdraw` template. Nothing is closed.
    - Without a valid ref, it gives `withdraw_which` with cards of the caller's open tickets, or
      `withdraw_none` if there are none.
  - `separate`: with a pending token that has `replaces`, the server confirms with `replace=false`. Without
    one, it is an ordinary `request`.
  - `confirm`: with a pending token, a typed yes confirms with `replace = bool(claims.replaces)`.
  - Repeat path: `_repeat_turn` runs when the preparer's `duplicate_of` matches and the category matches.
    If the new words name a room code, a room number or a building letter that the open ticket's text does
    not, and the old text named a place, the turn returns the correction proposal. It no longer comments
    on the old ticket.
  - `chat` and `decline` replies that claim a ticket was recorded or closed ("I have closed…", "has been
    recorded", "تم إغلاق/تسجيل/إلغاء") are replaced by the template.
- **Confirm with replace** (`_confirm_claims(..., replace=)`, from both `POST /v1/chat/confirm` and the in-turn
  `confirm`/`separate`).
  1. The duplicate guard skips the ticket the token replaces.
  2. The triage opens the corrected ticket.
  3. If `replace` is true and the token's `replaces` is set and a ticket was opened, `_close_replaced`
     reloads the old ticket. It goes on only if the request alias is the caller's and the status is
     `new` or `in_progress`. Then:
     - it adds the public comment `Closed by the requester: replaced by #<NEW> (corrected details).`;
     - it closes the ticket with `student_action(old, caller, close)`;
     - both deliveries go to `later`.
  4. `closed_ticket` is the old ticket as a card with status `closed`.
  - `replace=true` without the claim, against a ticket that is no longer open, or against someone else's
    ticket closes nothing, and `closed_ticket` is null.
  - The in-turn response also puts the closed card in `tickets`.
- **Route.** There is no code change: `ChatConfirmRequest.replace` reaches `ChatUseCase.confirm(cmd)`. An HTTP
  test covers it.

### Decisions

- **Comment before close (deviation from the spec order).** The spec says close, then comment. In
  `TicketLifecycleUseCase`, a requester comment on a solved or closed ticket reopens it (row 12). So the
  comment goes first, then the close. If the close then fails, which is rare because the status was checked
  just before, the comment remains and the ticket stays open. This is logged.
- **Two office emails.** Replacing a ticket sends the office the requester-reply email for the comment and
  the closed email. That is the existing behaviour of these two lifecycle actions.
- **`separate` without a correction is a request, not a confirm.** This way a model mistake cannot record an
  unrelated pending proposal.
- **The replay of a confirmed token returns the stored result.** That includes `closed_ticket`. A second
  confirm of the same token with a different `replace` value changes nothing.
- **Mock fixtures.** These are new: `chat_turn_status`, `chat_turn_correction` and `chat_turn_withdraw`
  (picked by an exact `messages` body), and `chat_confirm_replaced` (picked by `replace: true`).
  `docs/api/endpoints.md` was regenerated with `python scripts/gen_api_docs.py`. `openapi.json` was not
  touched.

### Edge cases for the web stream

- `correction` always comes together with `proposal`.
  - Confirm with `{proposal_token, replace: true}` for "Yes, replace #n", or `replace: false` for "separate".
  - `closed_ticket` can still be null with `replace: true`. This happens when the old ticket was closed or
    solved in the meantime, or the corrected request became an FAQ answer with no ticket. Show only the new
    ticket then.
- A typed "yes" on a correction replaces. A typed "it's a different problem" keeps both. Both come back as
  a normal recorded-ticket turn (`ticket_id`, `clear_proposal: true`). On a replace, `tickets[0]` is the
  closed old ticket.
- `withdraw` closes nothing.
  - Call `POST /api/ai/tickets/{withdraw.ticket_id}/student-action` with `{action: "close"}`. Closing an
    already closed ticket is a no-op 200.
  - When the ref was missing or invalid, the response has no `withdraw` but `tickets` (the open ones) with
    the `withdraw_which` reply. Render them as cards the student can pick from.
- `tickets` can appear on `status` turns, on `withdraw_which` turns and on replace confirms. Statuses are
  `new`, `in_progress`, `solved` and `closed`. `merged` never appears from the chat because merged tickets
  are excluded, but the type allows it.
- A correction can first come back as a clarifying question, with no proposal and no correction. The next
  turn usually brings the correction again.
- Card `title` is the ticket title, or "<Category> request" when it is empty. `office` is the D-005 code.
